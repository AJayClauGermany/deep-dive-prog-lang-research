# Authoring guide

This catalog collects literature for **comparing computer languages** (programming, query, configuration,
markup, data, hardware, theoretical models, ...). Every entry is a link plus enough metadata to find
"everything about concept X across languages" later.

## Source levels

| Level | Name | What belongs here | Typical `kind`s |
|---|---|---|---|
| 0 | Source code | Real implementations: compilers, interpreters, runtimes, standard libraries, machine-readable grammars, conformance suites. Shows *how a language can be implemented*; it does **not** define the language. | `implementation-repository`, `implementation-source` (a file/dir), `reference-implementation`, `standard-library-source`, `grammar-source`, `conformance-tests`, `tooling-source` |
| 1 | Primary | What *defines* the language independent of code: standards, specifications, official reference manuals, official library references, proposals (PEP/RFC/JEP/...), formal semantics, the designers' defining papers, design documents, release notes. | `standard`, `standard-draft`, `specification`, `reference-manual`, `library-reference`, `grammar`, `proposal`, `proposal-index`, `formal-semantics`, `original-paper`, `design-document`, `release-notes` |
| 2 | Secondary | Explains or analyses the primary sources: tutorials (including official ones), books, guides, courses, by-example sites, papers *about* the language, history/retrospectives, "X for Y programmers" comparisons, internals guides. | `tutorial`, `book`, `guide`, `course`, `by-example`, `cheatsheet`, `article`, `paper`, `history`, `video`, `style-guide`, `faq`, `interactive`, `comparison-guide`, `internals-guide` |
| 3 | Tertiary | Collections/summaries of other sources: Wikipedia, esolangs.org, Rosetta Code, PLDB, nLab, awesome-lists, comparison tables, benchmarks. | `encyclopedia`, `wiki`, `catalog`, `comparison-table`, `curated-list`, `bibliography`, `benchmark`, `code-collection`, `index` |

Rules of thumb: an *official tutorial* is level 2; an *official reference/spec* is level 1; a freely available
working draft of an ISO standard is level 1 `standard-draft`; a paper by the designers that introduces/defines the
language is level 1 `original-paper`, while a HOPL retrospective is level 2 `history`.

## Files

* `data/concepts.json` – the fixed concept taxonomy (ids such as `conditionals`, `pattern-matching`, `garbage-collection`).
* `data/languages/<id>.json` – one file per language (schema: `schema/language.schema.json`). **`data/languages/go.json` is the model to imitate.**
* `data/general/<id>.json` – cross-language resource collections (schema: `schema/general.schema.json`).
* `catalog.json` – generated by `tools/build.py`; never edit by hand.

## The point of the exercise: concept-tagged deep links

The catalog is valuable when one can ask "show me *if statements* in every language at every level".
So do not stop at whole-document links. For each language add **section-level deep links** and tag them:

* Level 1: the spec/reference section for the concept (e.g. `https://go.dev/ref/spec#If_statements` → `["conditionals"]`).
* Level 2: the tutorial/book chapter for the concept.
* Level 0: the source file that implements the piece (lexer, parser, type checker, evaluator, GC, scheduler, a builtin type...).
* Level 3: usually whole-language (Wikipedia article, Rosetta Code category, PLDB page, esolangs page).

Tagging rules:

* Use only ids from `data/concepts.json`. Read that file first. If something important has no fitting id, use the nearest
  one and mention the gap in your final report – do not invent ids.
* Tag a resource with a concept only if **that exact URL substantively covers it**. A whole-book link must not be tagged
  with thirty concepts; give it 0-3 broad tags (e.g. `hello-world`, `history`, `design-rationale`, `grammar`, `type-system`, `standard-library`) and add separate
  `"scope": "section"` entries for chapters.
* One resource may carry several concepts when the section really covers them (a "Control flow" chapter → `conditionals`, `loops`, `switch-case`).
* Prefer the taxonomy's general ids across language kinds so things line up: SQL `CASE` and `WHERE`-less conditional functions → `conditionals`;
  XSLT `xsl:if`/`xsl:choose` → `conditionals`; Makefile conditionals → `conditionals`; lambda-calculus Church booleans → `conditionals` + `encodings`;
  Turing-machine transition tables → `automata`; a YAML spec's "Anchors and aliases" → `references-anchors`.
* The baseline concepts to try to cover with level-1 deep links for any language where they make sense:
  `lexical-structure`, `comments`, `literals`, `variables`, `scope`, `primitive-types`, `strings`, `arrays`/`lists`, `maps-dictionaries`,
  `records-structs`, `conditionals`, `switch-case`/`pattern-matching`, `loops`, `functions`, `closures`, `exceptions`/`error-handling`,
  `modules`/`imports`, `operators`, `type-system`, `type-conversion`, `generics`, `classes`/`interfaces-protocols`, `concurrency`,
  `memory-management`, `macros`, `standard-library`, `grammar`, `program-structure`, `ffi`.
  For non-programming languages use the `data`, `query`, `theory`, `hardware` concept groups the same way.

## Depth tiers

* **Tier A** (flagship languages named in your assignment): 60-150 resources (do not exceed ~150); thorough concept deep links at levels 1 and 2,
  10+ level-0 source files with concept tags, several implementations, the proposal process, formal semantics where they exist, history papers.
* **Tier B** (everything else that is real and documented): 12-25 resources; all four levels where they exist, and deep links for at least the
  core concepts the documentation has anchors/pages for.
* **Tier C** (obscure/historical/esoteric/theoretical where little exists): 4-10 resources; whatever genuinely exists
  (original paper or manual scan, a surviving or reconstructed implementation, an encyclopedia/wiki entry).

Breadth across the assigned list matters more than perfecting one language: finish every id of the batch before deepening any file.
Tier A must still be genuinely deep, but stay inside the range.

## Field guidance

* `id`: kebab-case, equals file name. Use the ids given in your assignment exactly.
* `categories`: from the schema enum. `defined_by`: what is authoritative (standard, spec, the reference implementation, a paper...).
* `level_notes`: say explicitly when a level is missing or unusual (e.g. "no specification; the reference implementation is the definition",
  "theoretical model – level 0 lists simulators/mechanisations", "standard is paywalled; final draft Nxxxx linked").
* `influenced_by` / `related[].id`: use catalog ids (see `tools/assignments.json` for all planned ids).
* Resource `title`: "<Document> — <section>" style so it reads well in a cross-language list.
* `implementation`: name it on level-0 entries (CPython, PyPy, GCC, Clang, rustc, ...). Include alternative implementations.
* `access`: mark paywalled standards/books honestly; when a standard is paywalled also add the free draft if one exists.
* `authors`, `year`, `version`: fill in for papers, books, standards, proposals.
* Papers: prefer an open URL (author page, arXiv, ACM open access, archive.org, bitsavers, softwarepreservation.org). `https://doi.org/...` is fine when no open copy exists.

## URL rules

* Only include URLs you have reason to believe are real, then **verify** them (below). Never fabricate a URL to fill a slot.
* Prefer canonical, stable URLs (`/current/`, `/stable/`, `/latest/` doc paths; versioned standards).
* GitHub source: `https://github.com/<owner>/<repo>/blob/<branch>/<path>` for files (verifiable) – prefer file links over `tree/` directory links.
  Use the real default branch name (`main`/`master`/`trunk`) or `HEAD`.
* Search-result pages, URL shorteners, tracking parameters and pirate copies are not acceptable.
* Wikipedia: English article URL; section anchors only if verified.

## Verification workflow (mandatory)

```
cd tools
python3 validate.py ../data/languages/<id>.json ...      # schema, concept ids, level/kind consistency, duplicates
python3 check_links.py --workers 2 ../data/languages/<id>.json ...
```

* `dead` → the URL is wrong or gone: find the correct URL (search the web / browse the site's table of contents with curl) or drop the entry.
* `anchor-missing` → the page exists but the `#fragment` is wrong: fetch the page (`curl -sL <url> | grep -o 'id="[^"]*"'`) and use a real id,
  or drop the fragment (and reconsider the concept tags). Leave an anchor only if the site builds ids with JavaScript and you confirmed it another way.
* `blocked` (403 etc.) and `repo-only` are acceptable for URLs you are confident about (rosettacode.org, ACM DL, ISO, doi.org and GitHub directory links
  always report this way from this sandbox). `github.com` pages cannot be fetched directly here; use
  `curl -sL https://raw.githubusercontent.com/<owner>/<repo>/<branch>/<path>` to read files and discover paths.
* `error` → rerun later; if it persists and you cannot confirm the URL, drop it.
* Re-run until no `dead`/`anchor-missing` remain. Run the checker on a few files at a time rather than everything at once.
